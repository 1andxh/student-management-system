# 0022. Teacher login credentials, teacher-facing "my classes"/gradebook, and Enrollment ownership scoping

## Status
Accepted

## Context
Raised by Solomon: teachers are admin-created (no self-signup) but there was no way for a teacher to ever actually log in — `TeacherService.create()` never created a linked `User`, and no credential-issuance endpoint existed (unlike Students, which got exactly this via `POST /students/{id}/credentials` in Stage 9). Separately, Solomon wanted a real teacher-facing API surface: a teacher should see only their own classes, their own assessments (already correctly scoped, ADR 0019), a gradebook for their own students, and their own profile with change-request capability (already fully built, Stage 3b/ADR 0014 — no work needed there).

Investigation before any design work confirmed the exact prior state: `Teacher.user_id` had no role-guard (could be linked to a `User` of any role, the exact class of bug Stage 9's security review found and fixed for Students), `GET /classes` is a deliberately open course catalog (ADR 0019's own reasoning — must not be restricted), `GET /enrollments` had zero TEACHER-ownership scoping at all, and no gradebook aggregate view existed anywhere.

Three genuine design forks were confirmed with Solomon before building, not decided silently: teacher "my classes" as a new additive endpoint (`GET /teachers/me/classes`) rather than restricting the already-open `GET /classes`; extending ADR 0019's ownership-scoping pattern to Enrollment for TEACHER (covering both reads and writes, matching how it covers both for Assessment/Grade); and building a real gradebook aggregate endpoint (`GET /classes/{class_id}/gradebook`, ADMIN+TEACHER only, roster limited to `EnrollmentStatus.ACTIVE`) rather than leaving it to the frontend to assemble from two already-scoped list calls.

## Decision

### Teacher login credentials
`TeacherRepository` gained the `add(entity, *, commit: bool = True)` / `commit()` / `rollback()` shape `StudentRepository` already has. New `TeacherService.generate_credentials(teacher_id) -> TeacherCredentialsRead` mirrors `StudentService.generate_pin()`'s exact atomic two-write pattern, but hands back a **real, usable password** (`secrets.token_urlsafe(16)`) rather than a discarded one — teachers log in via the existing, already role-agnostic `POST /auth/login` (email+password), not a new PIN mechanism, so no auth-domain changes were needed. New route `POST /teachers/{teacher_id}/credentials`, admin-only, doubles as a password-reset endpoint on an already-linked teacher (same precedent as the Student PIN flow). The reset path fails closed (`UserNotFoundError`) rather than resetting a non-`TEACHER`-role account's password if a pre-Stage-10 row was linked before the next decision existed.

New `TeacherService._require_teacher_role_user()` mirrors `StudentService._require_student_role_user()` exactly, closing the same class of role-confusion bug found and fixed for Students in Stage 9 (a `Teacher.user_id` could previously be linked to a `User` of any role) — called from both `create()` and `update()` whenever `user_id` is being set.

### `GET /teachers/me/classes`
Purely additive — reuses the already-existing `ClassRepository.list_by_teacher_id()`, no change to `GET /classes` itself, which remains the deliberately open course catalog ADR 0019 established. No explicit role gate beyond authentication, matching `GET /teachers/me`'s existing pattern; a non-teacher caller gets `TeacherHasNoLinkedRecordError`.

### Enrollment ownership scoping
Extends ADR 0019's exact mechanism (`_check_owns_class`, `NotYourClassError` 403 not 404, explicit `class_id` not owned → rejected, omitted → auto-restricted to owned classes, `ADMIN`/`SUPER_ADMIN` unrestricted) to `EnrollmentService`, covering `enroll`/`get`/`list`/`drop` — both reads and writes, matching how ADR 0019 covered both for Assessment/Grade. Duplicated the `_check_owns_class`/`_get_my_teacher_id` helper pattern into a third service rather than extracting a shared base, deliberately consistent with ADR 0019's own on-the-record reasoning for per-service helpers over a shared class — revisit only if a fourth near-identical copy appears, not now.

**Deliberately not addressed this stage, flagged explicitly**: `EnrollmentService` still has no STUDENT self-scoping — a STUDENT-role caller sees every enrollment in the system, unrestricted, the same as before this stage (confirmed pre-existing behavior, not a regression; explicitly asserted by `test_list_as_student_role_unaffected_by_teacher_scoping`). This was scoped out of the settled Stage 10 contract (which only asked for TEACHER scoping) and surfaced independently by the post-implementation `security-auditor` review as a Medium finding, since `GradeService` already treats "which rows a STUDENT may see" as security-relevant (ADR 0018) and enrollment data (which classes a student is in) is arguably comparable in sensitivity. Not fixed in this stage — presented to Solomon as an explicit follow-up decision, not silently patched or silently ignored.

### `GET /classes/{class_id}/gradebook`
New endpoint on `classes_router`, deliberately nested (`/{class_id}/gradebook`) rather than following ADR 0020's flat/query-param list convention — a single composite object keyed to one required class, not a filtered collection, so the convention doesn't apply. Orchestration lives on `GradeService` (`assessments/service.py`), which already depends on every data source needed (`AssessmentRepository`, `StudentRepository`, `EnrollmentRepository`, `ClassRepository`, `TeacherRepository`) from Stage 7's "grading requires active enrollment" rule — no new domain or service class. Gated `ADMIN`+`TEACHER` only, deliberately excluding `STUDENT` — this endpoint returns an entire class's roster and every student's scores in one response, a materially different exposure than the existing self-scoped `GET /grades`, which a `STUDENT` still uses unchanged for their own grades. Roster is `EnrollmentStatus.ACTIVE` only (a `DROPPED`/`COMPLETED` student's `Grade` rows still exist but don't appear in this view — confirmed scope with Solomon, not an oversight). Response `scores` is a `dict[assessment_id, Decimal | None]` per student — self-describing, can't silently desync from the column list; `None` for ungraded, never omitted.

Two new small repository methods needed `from __future__ import annotations` added to their files (`teachers/service.py`, `students/repository.py`, `assessments/repository.py`, `enrollments/repository.py`) before adding a `list[...]`-returning method after an existing `list()` method in the same class body — the exact annotation-shadowing bug ADR 0018/0019 already hit twice, now hit and fixed proactively rather than reactively in every file this stage touched that needed it.

## Security review
`security-auditor` reviewed the new credential-issuance logic and the new/extended access-control mechanism (this project's standing rule for any auth/RBAC-touching change) and confirmed sound: the generated teacher password is CSPRNG-backed (128 bits), never logged or persisted in plaintext, and the reset-path fails closed correctly; the `_require_teacher_role_user` guard has no gap versus its Student equivalent; every Enrollment TEACHER-ownership check runs before mutating/returning data and fails closed on an unexpectedly-missing `Class` row (not the fail-open pattern ADR 0019 previously fixed elsewhere); the gradebook endpoint is unreachable by `STUDENT` under every path including a genuinely-enrolled student, and a `TEACHER` cannot view another teacher's gradebook; no SQL injection risk in any new repository method; `current_user` is server-derived only on every new/changed route. The one Medium finding (STUDENT self-scoping gap on Enrollment) is documented above as a deliberate, surfaced-not-silent scope boundary, not a missed fix.

## Consequences
- The `secrets.token_urlsafe(N)` → hash → return-once pattern is now precedent for both PIN-only (Student, discarded) and real-password (Teacher, usable) credential issuance — a future third role needing generated credentials should reuse whichever shape fits (discarded vs. real) rather than inventing a third mechanism.
- `EnrollmentService` now depends on `TeacherRepository` in addition to `ClassRepository`/`StudentRepository` — a new one-way fan-in edge, not a cycle, consistent with every other cross-domain dependency in this codebase.
- `classes/router.py` now depends on the `assessments` domain (`GradeService`, its repositories, its schemas) for the gradebook route — the first router file in this codebase to reach into a domain's `service.py` this way rather than just its own domain's; no cycle introduced (`assessments` doesn't import back from `classes.router`).
- **Open decision, not yet made**: whether `EnrollmentService` should gain STUDENT self-scoping, matching `GradeService`'s precedent. Bring this back as an explicit question before treating Enrollment's current open-read behavior as settled long-term.
- 558/558 tests passing (489 pre-Stage-10 + 69 new for teacher credential issuance/reset, the `_require_teacher_role_user` guard, `GET /teachers/me/classes`, the full Enrollment ownership matrix, and gradebook assembly/scoping), independently re-verified by rebuilding and re-running the full suite directly, plus reading the gradebook assembly test and the STUDENT-403 gradebook test directly against the settled contract — not inferred from either subagent's own report.
