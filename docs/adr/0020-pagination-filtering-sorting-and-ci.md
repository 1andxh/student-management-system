# 0020. Pagination, filtering, sorting, and CI

## Status
Accepted

## Context
Stage 8 ("polish", deliberately left as stretch/scope-TBD in the original plan). Two pieces were chosen out of the three candidates presented (pagination/filtering/sorting, a seed/demo data script, CI on GitHub) — the seed script was declined.

## Decision
- **Pagination is header-based, not an envelope.** `limit`/`offset` query params (`sms.core.pagination.pagination_params`, `limit` capped `[1, 200]`, default 50), total count reported via an `X-Total-Count` response header. The response body stays a bare array (`response_model=list[EntityRead]`, unchanged) on every one of the 12 list endpoints. Chosen specifically to avoid a large, low-value blast radius: an envelope shape (`{items, total, ...}`) would have required updating every existing list-endpoint test's response-shape assertion across ~10 domains, for a shape choice with no clear correctness benefit over a header.
- **Sorting is a fixed default (newest-first by each entity's own timestamp field), not a configurable `?sort_by=` feature.** `Student.created_at`, `Teacher.created_at`, `TeacherChangeRequest.created_at`, `User.created_at`, `AuditLog.created_at`, `AcademicYear.created_at`, `Term.created_at`, `Subject.created_at`, `Class.created_at`, `Enrollment.enrolled_at`, `Assessment.created_at`, `Grade.graded_at` — all descending. A generic arbitrary-field sort was judged to be real scope beyond "polish" (whitelist validation per domain, more query-param surface), not built.
- **New filters only where they mirror an existing FK relationship** ("browse the hierarchy" queries): `Term` by `academic_year_id`, `Class` by `term_id`/`subject_id`/`teacher_id`, `Assessment` by `class_id`. Arbitrary-field filtering (e.g. `Student` by `enrollment_status`, `User` by `role`) was deliberately not added — out of scope for what pagination itself needed.
- **`AssessmentService.list()`'s new `class_id` filter reuses `GradeService.list()`'s already-established TEACHER-ownership interaction pattern exactly** (ADR 0019): an explicit `class_id` a TEACHER doesn't own raises `NotYourClassError` (403); omitting it silently restricts results to their owned classes; ADMIN/SUPER_ADMIN are unrestricted either way. Not a new design decision — extending an existing one to a second endpoint that gained a filter capable of exercising it.
- **`AuditLogRepository.list()`'s ordering moved from `AuditService.list_all()`'s Python-side `sorted()` into the DB query** — a genuine revisit of ADR 0011's explicit "sorting is a service/consumer concern, don't reintroduce a repository-level `ORDER BY` without reason" note, not a silent reversal. The new reason: pagination requires the database to order rows *before* slicing via `LIMIT`/`OFFSET` — sorting a subset client-side after the DB has already truncated it can't produce a correct page.
- **`core/pagination.py`'s `paginate()` helper runs two queries** (one `COUNT(*)` over the caller's already-filtered statement, one with `LIMIT`/`OFFSET` applied) rather than a single window-function query. Simpler, more portable, and list endpoints here aren't hot paths — not worth the added complexity of `ROW_NUMBER() OVER (...)` for this project's scale.
- **CI runs natively (`uv sync` + `pytest`), not through Docker.** The containerized dev workflow (ADR 0003) exists specifically to work around this machine's WSL2 port-forwarding flakiness — a constraint that doesn't exist on GitHub's own runners. CI only spins up one Postgres service (matching `DATABASE_URL_TEST`), since `pytest` never connects to the dev database. No separate "apply migrations" CI step — `tests/conftest.py`'s `apply_migrations` fixture (`autouse`, session-scoped) already runs `alembic upgrade head` itself at test-session start, same as the local Docker flow; a duplicate step would just be redundant.

### A real, transaction-scoped Postgres interaction found while testing this
Postgres's `func.now()`/`CURRENT_TIMESTAMP` (the `server_default` every `created_at` column uses) is **transaction-scoped, not statement-scoped** — every `INSERT` within one transaction sees the same "now" value. Combined with `db_session`'s SAVEPOINT-based per-test isolation (ADR 0007 — the whole test runs inside one outer transaction), multiple rows created within a single test previously got *identical* `created_at` timestamps, making the new `ORDER BY created_at DESC` nondeterministic among ties whenever a test needed to assert on ordering. Fixed test-side only (no production or `conftest.py` change) by giving rows explicit, distinguishable `created_at` values in the fixtures that need deterministic ordering — the same override mechanism every other fixture kwarg already uses.

## Consequences
- Any future list endpoint should default to the same shape: `limit`/`offset` via `Depends(pagination_params)`, `X-Total-Count` header via a `Response` parameter, `paginate()` in the repository, newest-first via the entity's own timestamp field unless there's a specific reason not to.
- A future need for user-configurable sorting (nothing currently planned) would need real design work — a per-domain whitelist of sortable fields, at minimum — not a bare `?sort_by=<column>` passthrough.
- Any test that creates multiple rows of the same entity within one test and asserts on their relative order must pass explicit, distinguishable `created_at`/`enrolled_at`/`graded_at` values — relying on insertion order or default timestamps to differ is not safe under this project's SAVEPOINT-based test isolation.
- The CI workflow (`.github/workflows/test.yml`) has not yet run for real — it's written and reasoned against the proven local flow, but only verified once actually pushed and triggered.
- 439/439 tests passing (390 pre-Stage-8 + 49 new for pagination/filtering/sorting), independently re-verified by rebuilding and re-running the full suite directly, plus reading a sample of the new tests (the timestamp-tie fix, the Assessment/Grade TEACHER-ownership-vs-explicit-filter interaction) against the settled contract — not inferred from the delegated test-writer's own report.
