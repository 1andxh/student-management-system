# 0014. Teacher self-service change requests

## Status
Accepted

## Context
Stage 3b, raised directly by Solomon while Stage 3 (Teachers, ADR 0013) was in flight: teachers can't directly edit their own `Teacher` record (mutations are `ADMIN`-only, staff/HR data). Rather than either leaving teachers with no path to correct their own info or opening `Teacher` mutations back up, a request/approve flow gives them a narrow, admin-gated path. Two real forks were raised as explicit questions before building, not decided silently: which fields are requestable, and whether a teacher can have more than one pending request at once.

## Decision
- **Requestable fields are `first_name`/`last_name`/`email` only.** `hire_date` (a historical HR fact) and `user_id` (account-linkage, security-sensitive) stay admin-only-direct via the existing `PATCH /teachers/{id}` — never routed through approval.
- **One pending request per teacher, enforced at the DB level, not just the service.** A partial unique index (`teacher_id` unique `WHERE status = 'pending'`) is the actual guard — approved/rejected rows don't count, so a teacher can resubmit once their prior request resolves. The service pre-checks too (nicer error message), same "pre-check narrows the window, doesn't close it" pattern as every other domain's `create()` (ADR 0004).
- **Lives inside `domains/teachers/`, not a separate domain.** `TeacherChangeRequest` is tightly coupled to `Teacher` (FK, shares meaning, `approve()` directly reuses `TeacherService.update()`) — splitting it out would add a domain boundary with no real decoupling benefit, the same reasoning ADR 0012 used in the other direction when auth/users *did* warrant separating.
- **`approve()` reuses `TeacherService.update()` rather than duplicating mutation logic** — same validation and uniqueness-race handling as a direct admin `PATCH`. If `update()` raises (the target email was taken by someone else between request and approval), the exception propagates before the request is marked approved, so it stays `PENDING` rather than recording an approval that didn't actually apply.
- **`GET /teachers/me` and `POST /teachers/me/change-requests` are gated on `get_current_user` only, no role check.** The real authorization boundary is "do you have a linked `Teacher` record" (checked in the service, surfaced as 404 via `TeacherHasNoLinkedRecordError`), not "are you `TEACHER`-tier" — nothing in the schema currently constrains `Teacher.user_id` to only reference `TEACHER`-role users, so an explicit role gate here would be enforcing an invariant that doesn't actually exist yet, not real defense.
- **Literal-path routes (`/teachers/me`, `/teachers/change-requests`) are registered before `/teachers/{teacher_id}`** — FastAPI matches routes in registration order, and a route declared after `{teacher_id}` would try (and fail, with a UUID-parsing 422) to match "me"/"change-requests" against that route instead of reaching the intended one.

### A real gap the delegated test-writing caught
`TeacherService.update()` (written in Stage 3, mirroring Students' original pattern) never pre-checked email/`user_id` uniqueness — it relied entirely on the real DB's `IntegrityError`, which works against Postgres but isn't simulated by the in-memory fake used in unit tests. This was never exercised before because no prior test updated a `Teacher` into a colliding email. `qa-engineer`'s test for `approve()` propagating a uniqueness conflict exercised it for the first time and failed genuinely. Two independent, compatible fixes landed: a production pre-check added to `update()` (matching `create()`'s existing pattern, closing the actual gap the contract had promised), and the fake's `add()` was separately improved by `qa-engineer` to simulate `IntegrityError` on a duplicate against a *different* entity — kept even though the production pre-check now intercepts first, since it makes the fake faithful to real DB behavior for any future path that reaches `add()` without going through `update()`'s pre-check.

## Consequences
- Any future domain that needs a similar "propose then approve" pattern (there's nothing else planned yet) should follow this shape: new model with a status enum + partial unique index for the "one open request" invariant, reuse of the target domain's existing mutation method for applying an approval rather than a parallel mutation path.
- If `Teacher.user_id` is ever constrained to only reference `TEACHER`-role `User`s, the `GET /teachers/me` reasoning above should be revisited — it may become correct to add an explicit role check at that point, but doing so now would be enforcing an invariant that doesn't exist.
- 147/147 tests passing (94 pre-Stage-3 + 24 Teacher CRUD + 29 change-request), independently re-verified after each fix, not inferred from either delegated test-writer's own report.
