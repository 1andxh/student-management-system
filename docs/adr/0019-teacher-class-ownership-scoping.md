# 0019. Teacher class-ownership scoping

## Status
Accepted

## Context
`security-auditor`'s Stage 7 review (ADR 0018) flagged, as an out-of-scope observation rather than a bug in what it was reviewing: any `TEACHER`-role user could read/write assessments and grades for *every* class, not just ones they actually teach. The user asked to resolve this before moving to Stage 8 (polish). Two real forks were raised and confirmed before building: whether the fix covers `Assessment` as well as `Grade` (yes), and whether it covers reads as well as writes (yes).

## Decision
- **Only `TEACHER` is restricted.** `ADMIN`/`SUPER_ADMIN` are fully unrestricted, unchanged. A `TEACHER`'s "own classes" = `Class` rows where `Class.teacher_id` matches their own linked `Teacher.id`, resolved via `TeacherRepository.get_by_user_id(current_user.id)` — the same lookup shape as the student self-view scoping (ADR 0018), now duplicated as a private helper in both `AssessmentService` and `GradeService` rather than shared, matching this codebase's existing preference for small per-service helpers over a shared base class.
- **403 (`NotYourClassError`, a new `PermissionDeniedError` subclass in `classes/exceptions.py`), not 404, for ownership violations** — deliberately the opposite choice from the student-vs-student grade case. A `Class`'s existence is already visible to any authenticated user via the unrestricted `GET /classes`, so there's nothing to hide; hiding it here would be inconsistent with what's already exposed elsewhere.
- **A `TEACHER` with no linked `Teacher` record owns zero classes** — same "no linked record → empty scope" precedent as the student case, not a distinct error.
- **`AssessmentService`'s methods all gained a `current_user` first parameter** (`create`, `get`, `list`, `update`, `delete`) — previously none of them needed one. `GradeService.create`/`update` gained the same; `get`/`list` already had it from the student-scoping work.
- **`list()` scoping differs by shape between the two services**: `AssessmentService.list(current_user)` takes no filters at all (it never did), so a `TEACHER` simply gets the full list intersected with their owned classes. `GradeService.list(current_user, *, class_id=..., ...)` already accepted an explicit `class_id`; when a `TEACHER` passes one that isn't theirs, that's treated as a clear violation (`NotYourClassError`), not silently filtered away — only the *absence* of an explicit `class_id` triggers the implicit "restrict to everything I own" behavior.
- **`AssessmentService.update()` checks ownership of both the assessment's current class and, if `class_id` is being changed, the new target class** — a `TEACHER` can't touch an assessment outside their classes, and can't move one into a class they don't teach either.
- **A second instance of the `date`/`date_type` class-body annotation-shadowing bug (ADR 0018) surfaced and was fixed**, this time with a method name instead of a field name: `ClassRepository` already had a method called `list`; adding `list_by_teacher_id(...) -> list[Class]` after it in the same class body meant the bare `list[...]` annotation resolved to the earlier method object, not the builtin, raising `TypeError: 'function' object is not subscriptable` at import time (crashed the whole app). Fixed with `from __future__ import annotations` at the top of `classes/repository.py` — makes annotations lazy (string-based) so this can't recur in that file regardless of method order, rather than the more fragile fix of just reordering methods. `qa-engineer` independently hit the identical bug in its own test-side `FakeClassRepository` and fixed it there via reordering instead (a different file, no conflict, just a different acceptable fix for the same root cause).

### Security review (post-implementation)
A `security-auditor` pass, applying the same standard as Stage 7's student self-view review (ADR 0018) — this is the same class of change (a new access-control mechanism), not just a CRUD consumer of `require_role`. No confirmed live exploit: all six specifically-checked items (every method actually enforces the check before mutating/returning data, `update()` checks both current and target class, `GradeService.create()` checks ownership before other validation, `list()`'s `class_ids` filter is real SQL not Python-side and can't be bypassed via other params, no-linked-`Teacher` is treated as owns-nothing everywhere, `current_user` is server-derived only) were verified sound.

One Low-severity design concern, presented by the reviewer as a question rather than a required fix, and applied: five call sites used `if related_row is not None: check_ownership()` instead of failing closed when the row was unexpectedly missing. Not currently exploitable — every FK involved (`Assessment.class_id`, `Grade.assessment_id`, `Class`'s own FKs) is `ON DELETE RESTRICT`, so the state these branches guarded against literally cannot occur while the referencing row exists. But it was inconsistent with how `_check_owns_class`/`_check_owns_assessments_class` themselves already fail closed, and fragile against a future schema change (`SET NULL`, a raw-SQL delete bypassing the ORM) silently reopening it as a real bypass with no test positioned to catch it. Fixed in all five sites (`AssessmentService.get/update/delete`, `GradeService.get/update`) — `GradeService.update()` was the most notable of the five, since its fail-open branch was also silently skipping the `ScoreExceedsMaxScoreError` re-validation, not just the ownership check. Confirmed as pure dead-code hardening: the full suite (390/390) passed identically before and after, since the guarded state is unreachable under the current schema.

## Consequences
- This same `date`/`date_type`-style shadowing risk (any field or method name identical to a builtin/type it's annotated with) can recur anywhere in this codebase, not just the two places it's been hit so far. `from __future__ import annotations` was applied narrowly (just the one broken file) rather than swept across the whole codebase pre-emptively — worth revisiting as a deliberate, scoped decision if it recurs a third time, not something to silently apply everywhere.
- A future `STUDENT`-vs-`TEACHER`-vs-`ADMIN` three-way scoping need (nothing currently planned) should follow this stage's pattern: resolve the caller's own linked record once per request via a small helper, branch on `current_user.role`, and pick 404-vs-403 deliberately based on whether the underlying resource's existence is already exposed elsewhere — not by default to either one.
- 390/390 tests passing (283 pre-Stage-7 + 107 for the assessments domain, which now supersedes and extends Stage 7's original 59). Independently re-verified by rebuilding and re-running the full suite directly, plus reading one of the new ownership-violation tests against the settled contract — not inferred from the delegated test-writer's own report.
