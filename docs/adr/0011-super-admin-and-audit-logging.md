# 0011. Super admin tier and audit logging

## Status
Accepted

## Context
ADR 0010's security review left two findings deliberately unresolved — no guard against an admin locking out the system by demoting/deactivating the last active admin, and no audit trail for admin actions — both explicitly framed as product decisions, not code fixes. The user addressed both directly on return: proposing a super-admin tier to oversee "terminal actions" on admin-tier accounts, and asking to build audit logging.

## Decision
- **`SUPER_ADMIN` is a true "super" role**, not just one more allowed value. `require_role(*allowed_roles)` treats a `SUPER_ADMIN` caller as satisfying *any* check, regardless of what was listed — every existing and future admin-gated route accepts it implicitly, without needing to remember to list it at each call site.
- **Two mechanisms together close the lockout loop, not just relocate it**: (1) any `PATCH`/`POST` that touches an admin-tier account's role or `is_active` — demoting, deactivating, or promoting someone *to* admin-tier — requires the acting user to be `SUPER_ADMIN`, not just `ADMIN`; (2) a specific invariant blocks any change that would leave **zero active `SUPER_ADMIN`s**, even for a `SUPER_ADMIN` acting on themselves or the last other one. Mechanism 1 alone would only push the same lockout risk up one tier.
- **Creating a regular `ADMIN` stays open to any existing admin/super-admin** — only creating a *new* `SUPER_ADMIN` is itself gated. Growing the admin pool isn't a lockout risk; only shrinking the super-admin pool is. (Confirmed directly with the user rather than assumed.)
- **`UserService.create`/`update` now take `acting_user`, not just the target and data** — the admin-tier protection depends on who's asking, not just what's being asked.
- **`domains/audit/` is a new, deliberately dependency-free domain** — `AuditLog` stores plain `UUID` columns for actor/target (DB-level `ForeignKey` by name, no Python import of `User`, no ORM `relationship()`). This lets `auth` depend on `audit` (to record events) without violating ADR 0006's "auth depends on nothing else" for auth's own models/service/repository. Only `audit/router.py` imports from `auth` (for RBAC gating on `GET /audit-log`) — that's expected and matches every other domain's router, which all depend on auth for gating; the dependency-free rule applies to a domain's core logic, not its HTTP layer.
- **Audit visibility is `SUPER_ADMIN`-exclusive**, not plain-admin — the log records admin-tier account changes, so reading it carries the same trust tier as making those changes.
- **The bootstrap script (`create_admin.py`) now creates a `SUPER_ADMIN`**, not a plain admin. There is no real acting user for the very first account — see the security review below for how this is represented.
- **Every `src/sms/**/__init__.py` now re-exports its package's core building blocks** (models, schemas, exceptions, repository, service — not routers, which stay explicitly imported by name in `api/router.py` since some domains have more than one). Two deliberate exclusions: `sms/__init__.py` does *not* re-export `app`/`create_app` — `main.py` builds the full app (including `configure_logging()`) as a module-level side effect, and re-exporting it at the top-level package would trigger that for any unrelated import under `sms.*` (confirmed directly: importing `sms.domains.auth` does not pull in `sms.main`). `domains/audit/__init__.py` was populated before `domains/auth/__init__.py` to keep the dependency direction explicit while writing them, though Python's import machinery resolves the actual chain regardless of file-write order.

### Security review (post-implementation)
A third `security-auditor` pass (same process as ADR 0008/0009/0010) found the safety mechanisms above had real gaps of their own — 3 applied directly, 1 (pagination on `GET /audit-log`) not fixed, consistent with this project's already-deferred Stage 8 pagination scope rather than a new decision made in isolation here:
- **High — the last-active-super-admin check itself had a TOCTOU race.** `count_active_super_admins()` was a plain read; two concurrent requests each demoting a *different* one of the last two active super admins could both read "2 active," both pass the `<= 1` check, and both commit — zeroing out the tier despite the invariant that was just built specifically to prevent that. Fixed with `SELECT ... FOR UPDATE` on the active-super-admin rows (`UserRepository.count_active_super_admins`), so a concurrent equivalent check blocks until the first transaction commits and re-reads the real post-commit count. This depends on nothing committing on that session between the locking read and the caller's own final commit — `UserService.update` now says so explicitly in a comment, since it's a fragile invariant to leave implicit.
- **Medium — the audit entry wasn't committed atomically with the mutation it records.** `UserRepository.add` and `AuditLogRepository.add` each independently called `session.commit()`, even though `UserService` wires both onto the same `AsyncSession` — a fault between the two left a privileged change durable with zero audit trail, undermining the actual point of building audit logging. Fixed by adding a `commit: bool = True` parameter to both `add()` methods (default preserves every other existing call site unchanged) — `UserService.create`/`update` now flush both writes, then issue one shared commit, with an explicit rollback on any failure in between.
- **Low — the `system_actor` bootstrap pattern (a fabricated, never-persisted `User` built solely to satisfy an authorization check) was safe today but a reusable footgun if the pattern were ever copied into request-handling code.** Fixed by making `UserService.create`'s `acting_user` parameter `User | None` — `None` unambiguously means "no real actor" (the bootstrap script's only use case) rather than a hand-built stand-in indistinguishable from a real authenticated user. The router's `Depends(_admin_only)` guarantees `acting_user` is never `None` on any HTTP path — only the bootstrap script's direct Python call passes it.

## Consequences
- Any future admin-gated route automatically also accepts `SUPER_ADMIN` — don't add `UserRole.SUPER_ADMIN` to `require_role(...)` allowlists by hand, it's redundant.
- A future write path for `User` role/`is_active` that bypasses `UserService.update` (there shouldn't be one, but if one is ever added) would skip both the admin-tier gating and the last-super-admin guard — those checks live in the service, not the model or a DB constraint, and must stay there or be duplicated deliberately.
- The Postgres `user_role` enum's `super_admin` value cannot be cleanly removed by `alembic downgrade` — Postgres has no `ALTER TYPE ... DROP VALUE`; the migration's downgrade only drops `audit_logs` and documents why the enum change isn't reverted.
- `sorted()` for newest-first audit ordering happens in `AuditService.list_all()`, not `AuditLogRepository.list()` — matching every other repository's `list()` in this codebase being unordered. A repository-level `ORDER BY` was tried first and reverted for this reason; don't reintroduce it without reason.
- `UserRepository.add`/`AuditLogRepository.add` now take `commit: bool = True` — any new call site that needs to participate in a multi-repository atomic write (the same shape Enrollment, per the original plan's Stage 6, was always expected to eventually need) should follow this same pattern, not commit independently and assume it's fine.
- The `FOR UPDATE` lock in `count_active_super_admins` is only effective because nothing commits on that session between acquiring it and `UserService.update`'s own final commit — a future refactor that adds an intermediate commit on the same request would silently reopen the race this fix closes.
