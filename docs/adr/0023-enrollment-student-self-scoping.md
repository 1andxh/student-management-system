# 0023. Enrollment STUDENT self-scoping

## Status
Accepted

## Context
ADR 0022's post-implementation `security-auditor` review surfaced a Medium finding that was explicitly left open rather than silently fixed or silently ignored: `EnrollmentService` had no STUDENT self-scoping at all. `_check_owns_class` returns immediately for any role that isn't `TEACHER`, and both read methods only branched on `TEACHER` — so a logged-in STUDENT could call `GET /enrollments` with no filters and receive every enrollment record in the system (every student/class/status pairing school-wide), or call `GET /enrollments/{id}` with an enumerated UUID and read any other student's enrollment.

This predated Stage 10 — it was not a regression introduced by the TEACHER scoping work, and the Stage 10 contract deliberately only covered TEACHER. But Stage 10 was the point where every one of these methods was touched, and the reviewer's argument was that enrollment data (which classes a given student is in) is comparable in sensitivity to grade data, which `GradeService` already self-scopes for STUDENT (ADR 0018). The user was asked whether Enrollment warranted the same protection or whether leaving it open was deliberate, and chose to close it.

## Decision
Mirror `GradeService`'s established STUDENT self-scoping shape (ADR 0018) rather than inventing a second mechanism:

- **New `EnrollmentService._get_my_student_id(current_user)`** — resolves the caller's own `Student.id` via the already-injected `StudentRepository.get_by_user_id`. No new dependency was needed; `EnrollmentService` already had `StudentRepository` for the enroll-time existence check.
- **`list()`**: a STUDENT caller has `student_id` forced to their own resolved id, overriding whatever was passed in the query — a student can still narrow *their own* results by `class_id`, but can never widen scope past themselves. No linked `Student` record → `([], 0)`, matching the existing "no linked record → empty scope, not an error" precedent used for both the TEACHER case here and the STUDENT case in `GradeService`.
- **`get()`**: **404 (`EnrollmentNotFoundError`), not 403** — deliberately the opposite call from the TEACHER branch in the same method, which raises `NotYourClassError` (403). The reasoning is ADR 0019's, applied per-resource rather than uniformly: a `Class`'s existence is already public via the unrestricted `GET /classes`, so a 403 there hides nothing; another student's *enrollment* is not public, so a 403 would itself confirm the row exists. `my_student_id` is resolved **before** the enrollment lookup, and all three STUDENT failure branches (nonexistent enrollment / someone else's enrollment / no linked record) do the same amount of work and raise the same error — indistinguishable in timing as well as response body, matching the security-auditor finding behind ADR 0018.
- **Unchanged**: ADMIN/SUPER_ADMIN stay fully unrestricted; the TEACHER class-ownership scoping added in Stage 10 is untouched. `enroll()` and `drop()` needed no change — they're router-gated to ADMIN+TEACHER (`_can_manage`), so a STUDENT never reaches them.

**Process note**: this was implemented in the main thread rather than delegated, per the `agent-team` gate check in this project's `CLAUDE.md` — it's a small, tightly-coupled change that mirrors an existing pattern exactly, i.e. the case where writing a delegation contract costs more than doing the work. Tests were written in the same pass, not by a separate `qa-engineer` dispatch.

## Consequences
- One pre-existing test had to be *replaced*, not just added to: `test_list_as_student_role_unaffected_by_teacher_scoping` explicitly asserted the old unrestricted behavior ("STUDENT must see the same unrestricted result set as before this stage"). That assertion encoded the gap as intended behavior, which is exactly why the reviewer's finding was worth surfacing rather than assuming the test suite would have caught it. It's now `test_list_as_student_returns_only_own_enrollments` plus sibling tests covering the `student_id` override, `class_id` narrowing, filtering by a class the student isn't in (empty list, *not* `NotYourClassError` — guards against a future reordering of the role branches), the no-linked-record case, and all three of `get()`'s indistinguishable failure branches (nonexistent id / someone else's / no linked record).

  The post-implementation `security-auditor` pass caught that an earlier draft of this ADR overstated that last point — only two of `get()`'s three STUDENT branches were actually tested; the plain nonexistent-id case was missing at both unit and HTTP level. Added rather than reworded, since the claim was the correct intent and the gap was real.
- The 404-vs-403 split *within a single method* (404 for the STUDENT branch, 403 for the TEACHER branch) is deliberate and now has precedent in two services. A future role-scoped read should make this choice per-resource — based on whether that specific resource's existence is already exposed elsewhere — not pick one uniformly for the whole endpoint.
- Both remaining role-scoping mechanisms in this codebase (`GradeService`, `EnrollmentService`) now duplicate `_get_my_student_id`/`_get_my_teacher_id` per service rather than sharing a helper, consistent with ADR 0019's stated preference. This is now a fourth near-identical copy across the codebase — the threshold ADR 0022 named for revisiting extraction has arguably been reached, so the next service needing it should trigger that discussion rather than a fifth copy.
- 572/572 tests passing (558 pre-change + 14 net new), verified by running the full suite directly. Worth noting for future sessions: the first "green" run after adding the last three tests reported the *old* count, because `docker compose run` uses the existing image and this project's image is `COPY`-based, not bind-mounted — `docker compose build api` (or `up --build`) is required first, or the run silently tests stale code. The count not moving is what caught it.

### Environment note (not a code decision)
The usual `docker compose up -d --build` failed during this change with `Bind for 0.0.0.0:8000 failed: port is already allocated` — a container from an *unrelated* project on the same machine held port 8000. Rather than stopping another project's container, the suite was run via `docker compose run --rm --no-deps api uv run pytest`, which doesn't publish ports and needs no compose-file change. Worth remembering as the workaround when this recurs; it's a machine-level collision, not a project bug.
