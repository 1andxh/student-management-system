# 0010. User/account management (admin API)

## Status
Accepted

## Context
Solomon asked directly whether the plan made room for admin API endpoints. It didn't, and checking surfaced a more fundamental gap: there was no way to create a `User` at all through the API — not even the first admin account. This ADR covers the resulting inserted stage (2c), executed autonomously (Solomon stepped away and asked this be run as a real test of the orchestration setup, with explicit boundaries: no commits/pushes, no unilateral decisions on any tradeoff-bearing finding).

## Decision
- **`UserService` is a new, separate service from `AuthService`**, even though both operate on the `User` table — the opposite call from Stage 2b's "keep `AuthService` unified for login/refresh/logout." There, the reasoning was shared failure modes and a single caller (the authenticating user themself); here, the caller (an admin managing *other* people's accounts) and the failure modes (validation/uniqueness vs. authentication) are genuinely different. Splitting is the right call in both directions, for different, specific reasons — not an inconsistency.
- **`/users` is its own top-level resource path**, not nested under `/auth` — `/auth/*` are flow actions (login, refresh, logout, me); `/users` is resource CRUD. Both routers live in `domains/auth/router.py`.
- **Admin-only, not admin+teacher.** Every route on `users_router` is gated by `require_role(UserRole.ADMIN)` alone — stricter than Students (which allows admin+teacher). Managing login accounts and roles is a different trust level than managing academic records.
- **No `DELETE /users/{id}`.** `PATCH .../is_active=False` is the established deactivation mechanism (mirrors how `Session` revocation already works) — a hard delete raises real questions about `Teacher`/`Student` rows linked via `user_id` that this stage doesn't need to answer.
- **`UserUpdate` deliberately excludes email and password.** Changing either needs its own more careful flow (email-change verification, password reset) — bundling them into a bare admin `PATCH` would be building that flow badly rather than not building it.
- **The `create()`/uniqueness pattern from ADR 0004 is reused as-is**: pre-check via `get_by_email`, then `IntegrityError` catch around the actual insert, both translating to the same `UserAlreadyExistsError` — same reasoning, same shape, third domain to use it (after Students and, implicitly, `Session`'s unique refresh-token-hash constraint).
- **The bootstrap problem is solved with a one-off script, not an API route.** `src/sms/scripts/create_admin.py`, run via `docker compose exec api uv run python -m sms.scripts.create_admin`, reads `ADMIN_EMAIL`/`ADMIN_PASSWORD` from environment variables (not `argv`, so the password never lands in shell history). An admin-gated endpoint can't create the first admin; an open "first user becomes admin" registration route is its own security surface not worth building for this project. The script goes through `UserCreate` and `UserService.create` — the same validation and uniqueness-race handling as `POST /users` — rather than re-implementing those checks against the `User` model directly.

### Security review (post-implementation)
A `security-auditor` pass (same process as ADR 0008/0009) found 7 issues; 5 applied directly (no real tradeoff), 2 held for Solomon's return since the review itself framed them as product decisions:
- **Applied — real, non-hypothetical race**: `get_by_email`'s case-insensitive lookup didn't match the case-*sensitive* `UniqueConstraint("email")`. Two concurrent creates with case-variant emails (`Admin@x.com` / `admin@x.com`) could both succeed, and a later `login()` for that address would then match two rows, raising an unhandled `MultipleResultsFound` — a self-inflicted denial-of-service on a specific account. Fixed with a functional unique index (`Index("uq_users_email_lower", func.lower(email), unique=True)`, `models.py`, migration `d3033f1c17ad`) plus a lowercase `field_validator` on `UserCreate.email`, so the DB constraint's semantics now match what the read path (and the comment already claimed) assumed.
- **Applied — bootstrap script under-defended the account everything else derives from**: the original script only checked truthiness on `ADMIN_PASSWORD`, skipping `UserCreate`'s min-8-character rule. Fixed by rewriting the script to construct and validate a real `UserCreate` and call `UserService.create()` — this also transitively fixed the `.local`-email footgun noted below (superseded, not just patched around) and added the missing `IntegrityError` guard (ADR 0004 consistency) for free, through reuse rather than three separate patches.
- **Applied**: rate limiting (`30/minute`) added to all four `/users` routes, matching the posture already established on `/auth/login`/`/refresh`/`/logout`.
- **Held for Solomon**: no guard against an admin demoting/deactivating themselves, or dropping the system to zero active admins, via `PATCH /users/{id}`. The auditor's own framing: "whether self-lockout prevention and last-admin protection are wanted at all, versus accepted as 'admin is a trusted role, footguns are the operator's problem,' is a product decision, not just a code fix." Not decided here.
- **Held for Solomon**: no audit logging (who/what/when) on admin actions — create, role change, activate/deactivate. Real gap, but needs its own schema/design decision rather than being bolted on unprompted.

## Consequences
- Any future domain needing the same "admin manages a resource that isn't itself the acting admin's own data" shape should look at this `UserService`/`users_router` split as the reference, not `AuthService`.
- Any future write path for `User.email` (there's currently only `UserService.create`, via either `POST /users` or the bootstrap script) must go through `UserCreate` or otherwise lowercase the value before insert — the functional index enforces uniqueness case-insensitively regardless, but a write that skips normalization would store a mixed-case email inconsistent with every other row.
- No password-reset or email-change flow exists yet — `UserUpdate`'s exclusion of those fields is a deliberate gap, not an oversight, but it means there's currently no way to fix a mistyped admin-created password other than direct DB access or waiting for that feature.
- Two open decisions remain genuinely open, not silently resolved: last-admin/self-lockout protection, and admin-action audit logging. Both need Solomon's input before either is built or formally deferred.
