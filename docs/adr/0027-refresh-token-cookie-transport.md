# 0027. Refresh token travels in an HttpOnly session cookie

## Status
Accepted. Supersedes the token-transport parts of ADR 0009 (the body-based `TokenResponse` and the `RefreshRequest`/`LogoutRequest` bodies). The rest of 0009 still stands: sessions, rotation, absolute expiry and uniform errors.

## Context
The project is getting an in-repo browser frontend (`web/`, a Vite + React SPA; see ADR 0028). Until now `POST /auth/login`, `/auth/login-pin` and `/auth/refresh` returned both tokens in the JSON body, and `/auth/refresh` and `/auth/logout` took the refresh token back in a JSON body (ADR 0009). That shape gives a browser client nowhere safe to keep a 30-day refresh token: anything JavaScript can read, injected script can read too, so storing it in `localStorage` turns any XSS bug into a 30-day session takeover.

Three options were weighed with Solomon: keep the API as-is and store the token in `localStorage` (no backend change, known XSS exposure); put a backend-for-frontend server in front of the API that holds the tokens (strongest, but a second server process to run and reason about); or have the API itself put the refresh token in an HttpOnly cookie. He chose the cookie.

## Decision
- **The refresh token is sent only as a cookie, never in a JSON body.** `sms_refresh`, with `HttpOnly`, `SameSite=Strict`, `Path=/auth`, and `Secure` driven by `settings.refresh_cookie_secure` (`_set_refresh_cookie` in `src/sms/domains/auth/router.py`). The response body carries only the access token (`AccessTokenResponse`). Keeping the token in the body *as well* was rejected: then JavaScript could still read it and the HttpOnly flag would protect nothing.
- **It is a session cookie: no `Max-Age`, no `Expires`.** Closing the browser ends the login. The server's 30-day absolute session expiry (ADR 0009) still applies within one browser session. This was Solomon's call after the security review (F2 below). The alternatives were a "keep me signed in" opt-in, or keeping 30-day persistence, which would have let the next person on a shared school computer reopen the previous person's session. Caveat: browsers that restore the previous session ("continue where you left off") can bring session cookies back. Logging out is still the only guaranteed end.
- **The access token stays in the body and lives only in the SPA's memory.** It is short-lived (30 minutes) and sent as a `Bearer` header, so `get_current_user` and every other route are unchanged. A page reload loses it, and the SPA gets a new one from `/auth/refresh`, which the browser authenticates with the cookie.
- **The cookie is handled at the HTTP boundary; `AuthService` doesn't know it exists.** The service returns a `TokenPair` (renamed from `TokenResponse`), and the router splits it (`_to_client`). Cookies are an HTTP transport detail, so they belong in the router. None of the service unit tests needed changes beyond the rename. `TokenPair` is deliberately not named "Response" and not exported from `sms.domains.auth`. Used as a `response_model` it would put the refresh token back in a body.
- **`/auth/refresh` and `/auth/logout` take no body, and both check the request's `Origin` (CSRF).** Once a credential is attached automatically, those routes can be forged. CORS doesn't stop that: it hides the *response* from a disallowed origin, but the request still runs. SameSite doesn't fully stop it either, because it's drawn around the *site*, not the origin. Every port on 127.0.0.1 is same-site, and so is every subdomain under a shared parent domain. `_require_allowed_origin` rejects a present `Origin` that isn't in `settings.cors_origins` with a 403. Browsers send `Origin` on every POST. A missing `Origin` means a non-browser client (curl, tests), which no other site can drive, so it's allowed. A required custom header was the other option; it was rejected because the Origin check gives the same protection without changing the contract for clients.
- **The cookie is parsed from the raw `Cookie` header, and two values fail closed** (`_refresh_cookie`). FastAPI's `Cookie()` parameter keeps the *last* of several same-named cookies. A cookie planted at a broader path or from a sibling subdomain (cookie tossing) would sort after the real `Path=/auth` cookie and win, quietly logging the victim into the attacker's session. `__Host-` was considered and rejected because it requires `Path=/`.
- **Uniform errors are preserved.** A missing, duplicated, unknown, expired or revoked token all raise the same `InvalidRefreshTokenError` (ADR 0008/0009). A failed refresh sets no cookie, because the exception handler builds a fresh response. Logout stays idempotent (no cookie, or an unknown token, returns 204) and always clears the cookie with the same `Path` it was set with; otherwise the browser treats the clearing header as a different cookie.
- **CORS origins are a setting, and `*` fails startup** (`settings.cors_origins`, validator in `src/sms/core/config.py`). With `allow_credentials=True`, Starlette doesn't refuse `*`: it echoes back whatever `Origin` the request sent, which would make every site a credentialed origin. `allow_headers` is narrowed to `Authorization` and `Content-Type`.
- **`Secure` defaults to `True`, and turning it off outside `ENV=local` fails startup.** This is the same fail-closed posture as the JWT-secret check.
- **The SPA calls the API directly across origins rather than through a dev proxy.** `127.0.0.1:5173` → `127.0.0.1:8001` is same-site, so a `SameSite=Strict` cookie is still sent. A path-rewriting proxy (`/api/auth` → `/auth`) was rejected because the browser matches cookie paths against the URL it sees, which would no longer match `Path=/auth`.
- **The shared test `client` fixture uses `https://test`** (`tests/conftest.py`). httpx's cookie jar, like a browser, won't send a Secure cookie over plain http, and ASGITransport otherwise ignores the scheme.

### Security review (post-implementation)
A `security-auditor` pass found nothing critical or high. It judged the cookie attributes, the clearing semantics, the uniform errors and the CORS allowlist correct. Of its findings:
- **Fixed directly (no real tradeoff):**
  - F1 forgeable refresh/logout: the Origin check.
  - F3 cookie tossing: duplicate cookies fail closed.
  - F4 the `*` footgun: the `cors_origins` setting and its validator.
  - F5 Max-Age resetting to 30 days on every refresh: moot once the cookie became a session cookie.
  - F6 the token pair exported as public API: the `TokenPair` rename, removed from `__all__`.
  - F8 Secure switchable anywhere: the `ENV=local` guard.
  - Two missing tests: a disallowed origin gets no `Access-Control-Allow-Origin`, and a failed refresh sets no cookie.
- **Brought to Solomon as a question:** F2, a persistent cookie on shared devices. He chose "always a session cookie".
- **Accepted, no code change:** F7, HttpOnly limits *exfiltration*, not *use*. Script injected into the SPA can still call `/auth/refresh` with the cookie and read fresh access tokens while the page is open. The cookie turns an XSS from a 30-day takeover into abuse while the page is open. It doesn't make XSS harmless. A strict Content-Security-Policy on `web/` is the complementary control (ADR 0028).

## Consequences
- **Breaking change for any existing client.** `refresh_token` is gone from every response body, and refresh/logout no longer accept one. The only client was the separate frontend this work replaces.
- **A non-browser client (curl, scripts) has to handle cookies** to refresh, e.g. `curl -c jar -b jar`. Logging in and calling routes with the access token are unchanged.
- **Every browser login ends when the browser closes.** No "remember me" exists. Adding one later means a `max_age` set only on opt-in. If that happens, Max-Age must be computed from the session's real `expires_at`, not reset to the full lifetime on every refresh.
- **Concurrent refreshes are now the frontend's problem to prevent.** Rotation (ADR 0009) guarantees that of two simultaneous refreshes with the same cookie, one gets a 401. A tab firing several requests that all hit 401 at once, or two tabs refreshing together, would log the user out. The SPA must make refresh single-flight within a tab and serialize it across tabs (ADR 0028).
- **Unverified: Safari and Secure cookies on `http://127.0.0.1`.** Chrome and Firefox treat it as a secure context. WebKit has historically refused Secure cookies over plain-http localhost. If Safari drops the cookie, login looks successful, then the first refresh fails and the user is logged out at 30 minutes. Check during frontend Stage F3. The escape hatch is `REFRESH_COOKIE_SECURE=false` in a local `.env`.
- **Pre-existing, made more visible by a real SPA client:** the login rate limit keys on `request.client.host`. Behind Docker port publishing every browser may share one bucket. Not changed here.
- Any future change to the cookie's name or path has to update `_set_refresh_cookie`, `_clear_refresh_cookie` and `_refresh_cookie` together. A clear that doesn't match the set silently leaves the old cookie in place.
- **A new cookie-authenticated route needs `_require_allowed_origin` too.** The Origin check is per-route, not middleware.
