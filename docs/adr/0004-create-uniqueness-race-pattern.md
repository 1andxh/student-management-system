# 0004. Student domain business-logic decisions

## Status
Accepted

## Context
Two decisions were settled during Stage 1 (Students) implementation itself, not during earlier planning: how `student_number` (the plan's Stage-1 deferred point) gets assigned, and how a domain service should actually guard a uniqueness constraint on create — the plan called for a `UniqueConstraint` on `email`/`student_number`, but a bare pre-check (`get_by_email`/`get_by_student_number` before insert) leaves a real check-then-create race window between two concurrent requests, per the standing guidance in this project's global CLAUDE.md that such races must be handled via the underlying system's actual failure mode, not just a pre-check.

## Decision
- **`student_number` is admin-supplied at creation** (a required field on `StudentCreate`), not auto-generated by the service. Kept minimal for this stage; auto-generation (e.g. `STU-{year}-{sequence}`) can be revisited later if wanted.
- **Uniqueness races are handled two ways at once, not one**: the service still does the cheap pre-check (`get_by_email`/`get_by_student_number`) to fail fast in the common case, but the actual guard is the DB's `UniqueConstraint`, and the service wraps the persistence call in a `try/except IntegrityError`, translating it into the same domain error (`StudentAlreadyExistsError`) the pre-check raises. Neither mechanism alone is sufficient: the pre-check alone has a race window; the constraint alone (uncaught) would surface as a raw 500 via the catch-all exception handler instead of a clean 409.
- **This is the intended pattern for every future domain's `create()`**, not a students-specific one-off — any domain with a uniqueness constraint on create should follow the same shape: pre-check for the fast path, `except IntegrityError` around the actual write for the race case.

## Consequences
- A future domain that only does the pre-check (no `IntegrityError` handling) should be treated as incomplete, not a stylistic variation — it has a live race condition.
- If `student_number` auto-generation is added later, this ADR's first point is what's being revisited, and the reason ("kept minimal for Stage 1") is not itself a reason to keep deferring it indefinitely.
