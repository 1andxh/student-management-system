# 0018. Assessments and grades

## Status
Accepted

## Context
Stage 7 — the last domain-building stage in the plan (Stage 8 is polish only). `Grade` is the first aggregate carrying genuinely private per-user data (a student's own academic record), which surfaced a real, pre-existing gap: `Student` (built in Stage 1, before `auth`/`users` existed at all) had no link to a `User` account, unlike `Teacher`, which got `user_id` specifically to support self-service (ADR 0013).

## Decision
- **`Student.user_id` added now** — nullable, unique, `FOREIGN KEY -> users.id ON DELETE SET NULL`, same shape and reasoning as `Teacher.user_id`. Raised as an explicit blocking question before proceeding (not silently patched in), since it's a schema change to an already-built, already-tested domain — the alternative (skip self-view, treat it as its own later stage, mirroring how Teacher change requests became Stage 3b) was presented as a real option and declined in favor of building it now.
- **`StudentService.update()` got the same uniqueness pre-check fix already established for `Teacher` (ADR 0014)** — applied to `email`/`student_number` as well as the new `user_id`, not just the field this stage strictly needed. This was done without a separate confirmation round: it's the same already-decided pattern (not a new design fork), and the method was already being touched for the `user_id` addition regardless.
- **Grade-entry mutations (`create`/`update`) are `ADMIN`+`TEACHER`** — the plan's wording ("enter/update grade (teacher)") read differently from assessment creation ("teacher/admin"), which could have meant a deliberate admin-exclusion. Confirmed as unintentional shorthand, not a real restriction — admins can enter/correct grades same as assessment creation.
- **Grading requires the student to be actively enrolled in the assessment's class** — raised as an optional addition (not explicitly asked for by the plan) and confirmed before building, since it's a real data-integrity gap ("grade a student who was never in the class") a cheap check closes. `GradeService.create()` checks `EnrollmentRepository.get_by_student_and_class(...).status == ACTIVE` before allowing a grade.
- **A `STUDENT`-role caller only sees their own `Grade` rows.** `GradeService._get_my_student_id()` resolves the caller's linked `Student` via `user_id`; `list()` force-overrides any `student_id` filter they pass (rather than rejecting a mismatched one) and returns `[]` if they have no linked `Student` at all (not an error); `get()` raises `GradeNotFoundError` — not `PermissionDeniedError` — for a grade that exists but isn't theirs, deliberately hiding whether it exists from a student probing another student's grade ID. `ADMIN`/`TEACHER` callers get no such restriction, matching every other domain's read precedent (no "teacher only sees their own classes" scoping was built — not hinted at by the plan, and Enrollment's own reads didn't do this either).
- **`GET /grades` supports `class_id`/`student_id`/`assessment_id` filtering** — `class_id` requires a join through `Assessment` since `Grade` has no `class_id` column of its own. Directly serves the plan's "teacher/admin see all for their class" language, read as: when a privileged caller looks at one class's grades, they see every student's row for it (the full set), in contrast to a student who'd only ever see their own row even within that same class.
- **A real, unrelated bug found and fixed along the way**: `date: date | None = None` in `schemas.py` — the field name is identical to its type. In a class body, Python evaluates the default-value assignment *before* the annotation, so by the time `date | None` is evaluated, the local name `date` has already been rebound to the just-assigned `None`, producing `TypeError: unsupported operand type(s) for |: 'NoneType' and 'NoneType'`. `models.py` had already avoided this defensively (`from datetime import date as date_type`); `schemas.py` hadn't applied the same aliasing. Fixed by aliasing consistently.
- **`db/session.py`'s engine now uses `NullPool` + `pool_pre_ping=True`**, raised directly by Solomon mid-stage. No connection reuse across requests, and pre-ping checks liveness before handing one out — a real cost (fresh connection setup per request instead of a warm pool) accepted specifically because this dev environment's DB container restarts independently of the API container often enough (WSL2 idle-shutdown, rebuilds) that a stale pooled connection failing mid-request is the more likely failure mode to guard against here, not raw throughput.

### Security review (post-implementation)
A `security-auditor` pass, warranted specifically because this is the first domain implementing real per-user ownership scoping (every prior domain either gates by role only or has no read restriction) — a bug here leaks one student's grades to another, a different failure class than a bad RBAC gate. No Critical/High/Medium findings. Explicitly verified and confirmed sound: the `list()` force-override can't be bypassed (filters are `AND`-chained, not `OR`, so a STUDENT can only narrow within their own grades, never expand into another's); `get()`'s 404-not-403 doesn't leak via response content; `current_user: User = Depends(get_current_user)` as a plain parameter enforces authentication identically to the `dependencies=[Depends(...)]` pattern used elsewhere (a style inconsistency, not a security gap); `Student.user_id`'s DB-level uniqueness prevents two `Student` rows ever resolving to the same caller; role is re-fetched fresh from the DB every request, not trusted from the JWT (no stale-privilege window).

One Low-severity finding, fixed directly (small, mechanical, completes the intent already stated in the code's own comment rather than adding new scope): `GradeService.get()` did one DB call for a nonexistent grade but two for someone else's grade before raising the same 404 — a timing side-channel partially undermining the point of using 404 instead of 403. Fixed by resolving `my_student_id` before checking whether the grade exists, so both branches do the same work. Practical exploitability was already assessed as low (UUIDv4 keyspace makes ID-guessing impractical on its own), but the fix was free enough not to leave it as an accepted-risk note instead.

One out-of-scope observation, deliberately not addressed here: `ADMIN`+`TEACHER` gates grade mutations, but any `TEACHER` can read/write grades for *every* class, not just ones they teach — a pre-existing role-only pattern matching every other domain (not a regression introduced by this stage's scoping work). Whether a `TEACHER` should be scoped to their own classes is a legitimate, separate design question for a future stage, not folded into this one. **Resolved immediately after this stage — see `docs/adr/0019`.**

## Consequences
- Stage 8 (polish) or any future stage adding another privileged-vs-self-scoped view should follow the `GradeService` pattern: resolve the caller's own linked record once (a small private helper, not inlined per-method), force-override filters for a restricted caller rather than validating-and-rejecting, and return "not found" rather than "forbidden" for someone else's row.
- `Student.user_id` being added this late means any earlier-created `Student` rows have `user_id = NULL` — expected and harmless (nullable + unique constraint allows any number of `NULL`s in Postgres), but a `Student` created before this stage has no self-view access until an admin links it via `PATCH /students/{id}` with `user_id` set.
- The `date`/`date_type` aliasing convention (established for `models.py` in this stage, now also in `schemas.py`) should be applied proactively any time a field name would otherwise collide with its own type name — this is a general Python gotcha, not specific to this codebase, and will recur if not watched for.
- 342/342 tests passing (283 pre-Stage-7 + 59 new), independently re-verified — both by rerunning the full suite directly and by reading a sample of the self-view test cases against the settled contract, not inferred from the delegated test-writer's own report (which itself also independently re-diagnosed the `date`/`date_type` bug rather than assuming it was fixed).
